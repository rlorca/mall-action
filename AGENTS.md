# AGENTS.md - read this first

This repository is a **benchmark: the same one-shot prompt given to different AI models**, not a single codebase.
Each implementation branch is one model's attempt; the value is in comparing them, so keep the runs comparable.

## Repository structure

| Ref | What lives there |
|---|---|
| `main` | ONLY this file, `README.md` and `one-shot-prompt.md`. No game code, no build files, no workflows. |
| `opus-5-5` | The implementation built by Claude Opus 5.5 (its own `README.md`, `AGENTS.md`, tests, CI). |
| `sonnet-5-5` | The implementation built by Claude Sonnet 5.5 (its own `README.md`, `AGENTS.md`, tests, CI). |
| `gh-pages` | Generated by CI. One folder per implementation (`opus-5.5/`, `sonnet-5.5/`) plus a landing `index.html`. Never edit by hand. |

The branches are **independent histories**: they share no commits with `main` or with each other. Do not merge
them or rebase one onto another.

## Before you touch anything

1. Work out which branch your task is about. Implementation work happens on the implementation branch only.
2. Read that branch's own `AGENTS.md` (architecture, rules that must hold, how to verify changes). This file only
   describes the repo layout; it says nothing about how a given game is built.
3. `one-shot-prompt.md` is the shared spec every implementation was built from. Treat it as read-only: changing it
   changes the experiment. Propose edits to the user instead of making them.

## Publishing

- Live site: `https://rlorca.github.io/mall-action/` (landing page), with each build under
  `/<model>-<version>/`, e.g. `/sonnet-5.5/` and `/opus-5.5/`.
- Each implementation branch carries its own `.github/workflows/pages.yml`. On every push to that branch it runs
  `npm ci`, `npm test`, `npm run build`, and only if all pass copies `dist/` into `<publish-dir>/` on the `gh-pages`
  branch. A failing test blocks the publish.
- Pages is served from the `gh-pages` branch (root), NOT from GitHub Actions artifacts, so several
  implementations coexist. The workflows share one `concurrency` group so they never push to `gh-pages` at once.
- Builds are served from a sub-path, so every implementation must build with relative asset URLs (`base: './'` in
  Vite) and must not assume it is served from `/`.

## Running a benchmark for a new model

1. Start from an EMPTY directory and a fresh session of the model. Give it `one-shot-prompt.md` verbatim as the
   only task (no hints, no extra instructions, no reference to other branches or their code).
2. Let it work autonomously to the brief's *Definition of done*. Human help is limited to what the harness needs
   (e.g. approving tool calls); do not steer the design. Note anything you did have to intervene on.
3. Record the run in the branch `README.md` under a "Benchmark notes" heading: model name and id, date, harness
   (e.g. Claude Code version), reasoning/effort setting, roughly how long it took, and any interventions.
4. Publish it as a new branch (below). Never overwrite or "improve" another model's branch to make it look better;
   fixes after the one-shot run go in later commits so the original result stays in the history.
5. Compare: does it build and pass its own tests, does it run without console errors, how much of the brief works,
   how does it play, code and test quality.

## Adding a new implementation

1. Create an orphan branch named `<model>-<version>` with dashes, e.g. `fable-5-1` (`git checkout --orphan ...`).
2. Give it a `README.md`, an `AGENTS.md`, tests, and `npm test` / `npm run build` scripts that output to `dist/`.
3. Copy `.github/workflows/pages.yml` from an existing implementation branch and change the branch name under
   `on.push.branches` and `PUBLISH_DIR` (dots for the folder, e.g. `fable-5.1`).
4. Add a row to the table in `README.md` on `main` and a link on the `gh-pages` landing page.
5. Push. Check the Actions tab, then load the published URL.

## Conventions

- Branch names use dashes (`sonnet-5-5`); published folders use dots (`sonnet-5.5`).
- The prompt is the fixed variable. If it must change, treat it as a new benchmark version and say so in `README.md`.
- Keep `main` tiny. If you are about to add a file to `main`, you are probably on the wrong branch.
- Do not delete or force-push implementation branches: their history is part of the comparison.
